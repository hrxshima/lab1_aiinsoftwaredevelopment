# Архитектурные правила и конвенции репозитория FinanceTracker

Проект представляет собой распределённую микросервисную систему на .NET (C#), включающую `auth-service`, `transaction-service`, `report-service` и `gateway`.

## 1. Тонкие контроллеры и разделение слоёв

* Контроллеры (`Controllers/*`) отвечают за обработку HTTP-запросов, получение параметров, проверку входных условий и формирование HTTP-ответов.
* Контроллерам запрещено напрямую обращаться к `DbContext` (`AuthDbContext`, `AppDbContext`) и репозиториям (`*Repository`).
* Доступ к бизнес-логике осуществляется через сервисы, внедряемые посредством Dependency Injection.
* Работа с базой данных выполняется на уровне репозиториев и сервисов, а не непосредственно в контроллерах.

## 2. Изоляция моделей базы данных через DTO

* EF Core-сущности из `Models/*` не используются как публичные контракты HTTP API.
* Входные и выходные данные API описываются отдельными DTO, размещёнными в `Dtos/` или `DTO/`.
* Преобразование сущностей базы данных в DTO выполняется за пределами контроллера.
* При добавлении нового API-эндпоинта следует создавать или переиспользовать соответствующий DTO вместо передачи EF Core-модели напрямую.

## 3. Группировка связанных DTO

* DTO одной функциональной области группируются в одном файле по шаблону `{Entity}Dtos.cs`, если это не требует отдельного файла по техническим причинам.
* Например, запросы и ответы для транзакций располагаются в `TransactionDtos.cs`, а для категорий — в `CategoryDtos.cs`.
* DTO не объявляются непосредственно внутри классов контроллеров.
* Для отдельных микросервисов, где DTO уже организованы по отдельным файлам, при добавлении новых типов следует придерживаться существующей структуры этого сервиса.

## 4. Интерфейсы сервисов и Dependency Injection

* Бизнес-логика реализуется в сервисах, доступных через интерфейсы (`I*Service`).
* Контроллеры используют интерфейсы сервисов, а не конкретные реализации.
* Взаимодействие с репозиториями также осуществляется через их интерфейсы (`I*Repository`).
* Новые сервисы и репозитории регистрируются в DI-контейнере соответствующего микросервиса в `Program.cs`, например:

```csharp
builder.Services.AddScoped<IService, Service>();
builder.Services.AddScoped<IRepository, Repository>();
```

## 5. Разделение внешнего и внутреннего API

* Пользовательские HTTP-эндпоинты размещаются в стандартных контроллерах, например `UsersController`, `TransactionsController` и `CategoriesController`.
* Эндпоинты, предназначенные для межсервисного взаимодействия, размещаются в отдельных контроллерах с префиксом `Internal`, например `InternalUsersController` и `InternalTransactionsController`.
* Внутренние эндпоинты используют отдельный маршрут `internal/...` и не смешиваются с пользовательскими маршрутами `api/...`.
* Взаимодействие между микросервисами выполняется через HTTP-клиенты и контракты, а не через прямой доступ к базе данных другого сервиса.

## 6. Получение идентификатора пользователя из JWT

* В `transaction-service` идентификатор пользователя из JWT извлекается через единый метод-расширение `User.GetUserId()`, определённый в `Extensions/ClaimsPrincipalExtensions.cs`.
* Контроллеры `TransactionsController` и `CategoriesController` не должны самостоятельно парсить `ClaimTypes.NameIdentifier`, `sub` или другие claims.
* При необходимости аналогичного подхода в другом микросервисе следует использовать отдельный общий helper/extension вместо дублирования логики извлечения идентификатора.

## 7. Единый подход к тестовой базе данных

* Тесты сервисов не должны повторно настраивать `DbContextOptionsBuilder` непосредственно в каждом тестовом классе.
* Для создания тестового контекста используется общий вспомогательный класс `TestDb` соответствующего микросервиса.
* Фабрика отвечает также за создание тестируемого сервиса с необходимыми зависимостями.

Пример:

```csharp
using var context = TestDb.CreateContext();
var service = TestDb.CreateTransactionService(context);
```

Таким образом, конфигурация тестовой базы данных и создание зависимостей централизованы в одном месте.
