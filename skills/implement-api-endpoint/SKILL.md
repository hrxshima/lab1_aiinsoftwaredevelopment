# Skill: Реализация нового API-эндпоинта

Используй этот алгоритм при добавлении нового API-эндпоинта или изменении существующего эндпоинта в репозитории FinanceTracker.

## Обязательные правила

* Сначала определи целевой микросервис (`auth-service`, `transaction-service`, `report-service` или `gateway`).
* Перед изменением файлов изучи существующую реализацию аналогичного функционала в этом микросервисе.
* Не переноси соглашения одного микросервиса в другой, если структура или реализация отличаются.
* Сохраняй существующую архитектуру и стиль целевого микросервиса.
* Не создавай новые архитектурные слои или зависимости без необходимости.

## Шаг 1. API-контракт (DTO)

1. Найди существующее расположение DTO в целевом микросервисе.
2. Для `transaction-service` связанные DTO группируй в `Dtos/{Entity}Dtos.cs`, например `TransactionDtos.cs`.
3. В других микросервисах следуй существующей структуре DTO этого микросервиса.
4. Используй `public record` для новых DTO, если существующие аналогичные контракты используют этот формат.
5. Не объявляй DTO внутри контроллеров.
6. Не создавай отдельный файл для DTO, если соответствующая функциональная область уже использует общий файл DTO.
7. Перед созданием нового DTO проверь, нельзя ли переиспользовать существующий контракт.

## Шаг 2. Слой данных

1. Сначала проверь, достаточно ли существующих сущностей и методов репозитория.
2. Если требуется новая операция с базой данных:

   * добавь метод в `Repositories/I*Repository.cs`;
   * реализуй его в соответствующем `*Repository.cs`;
   * используй `DbContext` только внутри репозитория.
3. Если требуется изменение модели данных, измени соответствующую сущность в `Models/`.
4. Не обращайся к `DbContext` или репозиторию непосредственно из контроллера.
5. Не добавляй новый репозиторий, если существующий репозиторий уже отвечает за нужную сущность и может безопасно выполнять новую операцию.

## Шаг 3. Бизнес-логика

1. Если для эндпоинта требуется новая бизнес-логика:

   * добавь метод в `Services/I*Service.cs`;
   * реализуй его в соответствующем `*Service.cs`.
2. Выполняй в сервисе:

   * бизнес-валидацию;
   * проверки существования данных;
   * проверки прав доступа;
   * вызовы репозитория;
   * преобразование сущностей в DTO.
3. Не возвращай `Models/*` из сервисного API, если результат предназначен для HTTP-контроллера.
4. Не помещай бизнес-логику в контроллер.
5. Если добавляется новый сервис, зарегистрируй его в `Program.cs` через интерфейс:

   ```csharp
   builder.Services.AddScoped<IService, Service>();
   ```

## Шаг 4. Контроллер

1. Для пользовательского API используй существующий публичный контроллер соответствующей сущности.
2. Для межсервисного API используй `Internal*Controller`.
3. Внутренние эндпоинты должны использовать существующий в микросервисе маршрут `internal/...`.
4. В контроллер внедряй интерфейс сервиса (`I*Service`), а не конкретную реализацию.
5. НЕ внедряй в контроллер:

   * `DbContext`;
   * `*Repository`;
   * конкретные реализации сервисов.
6. Контроллер должен:

   * получить HTTP-входные данные;
   * передать их сервису;
   * вернуть результат в формате HTTP API.
7. Не дублируй в контроллере бизнес-логику, которая уже находится в сервисе.

## Шаг 5. User ID

Это правило применяется только к `transaction-service`.

При получении идентификатора текущего пользователя используй:

```csharp
var userId = User.GetUserId();
```

НЕ извлекай User ID вручную через:

```csharp
User.FindFirst(...)
User.FindFirstValue(...)
ClaimTypes.NameIdentifier
"sub"
```

Не дублируй логику извлечения User ID в новом коде.

## Шаг 6. Межсервисное взаимодействие

Если новый эндпоинт предназначен для другого микросервиса:

1. Размести endpoint в `Internal*Controller`.
2. Проверь существующий HTTP client вызывающего сервиса.
3. Используй существующий контракт и формат ответа, если они подходят.
4. Не реализуй прямой доступ одного микросервиса к базе данных другого микросервиса.
5. Если требуется новый HTTP-вызов, добавь его в существующий client/service слой соответствующего микросервиса.

## Шаг 7. Тесты

1. Найди существующие тесты соответствующего сервиса перед добавлением новых.
2. Для тестов с базой данных используй существующий `TestDb`.
3. НЕ создавай собственный `DbContextOptionsBuilder` в каждом тестовом классе, если для данного микросервиса уже существует `TestDb`.
4. Добавь тесты для:

   * основного успешного сценария;
   * ошибок/валидации, релевантных новому эндпоинту;
   * проверки прав доступа, если она присутствует в функциональности.
5. Не изменяй существующие тесты только для обхода ошибки нового кода.

## Шаг 8. Проверка после реализации

Перед завершением проверь:

* DTO находятся в правильном месте;
* существующий DTO не был продублирован;
* контроллер не обращается к БД напрямую;
* бизнес-логика находится в сервисе;
* доступ к данным выполняется через репозиторий;
* сервисы и репозитории зарегистрированы в DI;
* EF Core-сущности не используются как HTTP-контракты;
* внутренние endpoints размещены в `Internal*Controller`;
* в `transaction-service` User ID получается через `User.GetUserId()`;
* соответствующие тесты добавлены или обновлены;
* изменения не нарушают существующую структуру целевого микросервиса.
